Claude Code 爆雷：你的 AI 助手正在把公司密钥「喂」给陌生人

前几天 HackerNews 上有个帖子火得一塌糊涂。

标题很直白：Claude Code 正在 GitHub 上无意间泄露大量敏感信息。

这不是什么玄学猜测，是 Anthropic 自己的工具翻车了。

事情起因很简单，但后果有点让人后背发凉。

不少开发者反馈，他们本地跑着 Claude Code，结果推送到 GitHub 的代码库里，赫然躺着 API Key、AWS 凭证，甚至公司内部的服务地址。

Ars Technica 最近发了篇深度报道，把这些案例串了起来。

核心问题出在「默认设置」上。

很多人不知道，Claude Code 在初始化时会生成一个 settings.json 文件。

这个文件本意是为了记录你的工作流偏好，比如默认模型、权限范围之类的。

但它太「贴心」了——贴心到有点多余。

它顺手把当前环境的变量、API Key 甚至部分路径信息也一并写进去了。

如果开发者没注意，直接把这个项目 push 到公开仓库，等于把自己公司的底裤亮给了全网。

我观察到一个现象：越是追求效率的开发者，越容易踩这种坑。

咱们用 Claude Code 是为了什么？

不就是想少敲几行代码，让 AI 帮你把逻辑跑通吗。

这种情况下，很少有人会去逐行检查生成的配置文件。

尤其是当这些文件静静地躺在 .claude/ 目录下，看起来人畜无害的时候。

还有一个更隐蔽的风险点。

有些团队为了省事，直接把整套环境配置同步到云端协作。

结果就是，一个人写了个脚本，带着他的个人 Key 上去跑。

整组人跟着他一起「裸奔」。

这事儿说出来可能没人信，但Ars的调查显示，GitHub 上能搜到不少类似的「翻车现场」。

有人甚至把数据库密码直接写进了 commit message 里。

当然，Anthropic 反应还算快。

官方很快发了公告，承认这是设计上的疏忽。

他们建议用户手动删除 settings.json，或者在 .gitignore 里加上排除规则。

但这能解决根本问题吗？

我觉得悬。

因为只要工具还在「默认开启」某些功能，就总会有人忽略它的存在。

技术圈一直有个迷思，叫「默认安全」。

意思是说，开发者理所当然地认为，出厂设置就是最安全的状态。

但现实往往很打脸。

很多工具的默认设置，优先考虑的是「易用性」和「开箱即用」，而不是「安全性」。

对于个人业余项目，这点疏忽顶多算是个教训。

但对于企业级应用，这就是炸弹。

想象一下，你的公司正在用 Claude Code 做一个内部系统的自动化运维脚本。

脚本里引用了内部的 Vault 凭证。

开发者觉得一切正常，顺手 commit 到了公司的内网 GitLab。

听起来很稳，对吧？

但如果哪天 he 手滑，把这个仓库设成了「公开」呢？

或者，这个仓库的代码被复制粘贴到了某个开源社区的项目里呢？

密钥一旦暴露，后续的渗透测试、权限提升、数据拖库，都是一瞬间的事。

这才是让我真正感到不安的地方。

我们总是过分关注 AI 工具本身的能力：

它写得准不准？快不快？是不是支持长上下文？

却很少去想，它在执行过程中，会不会把你的「家当」偷偷搬出来晒。

这次 Claude Code 的事件，与其说是技术 bug，不如说是安全意识的一个警钟。

它提醒我们，在享受 AI 提效红利的同时，别把信任完全托付给工具。

毕竟，AI 不知道什么是「敏感信息」，它只知道如何完成任务。

如果你也在用这类工具，我有几条建议，希望能帮到你。

第一，养成检查 .gitignore 的习惯。

确保所有潜在的配置文件、环境变量文件都被拦截在仓库之外。

第二，不要信任任何工具的默认设置。

每次初始化新项目，手动过一遍配置项，关掉那些看起来多余的「便利功能」。

第三，定期扫描你的历史提交。

用一些开源的安全扫描工具，看看以前有没有漏掉什么 sensitive data。

第四，也是最重要的一点。

把「安全」和「效率」分开来看。

AI 可以帮你提效，但不能替你做安全决策。

这条流水线的尽头，还得有人类来把关。

说实话，我也在用各种 AI 编程助手。

效率确实高了不少，以前一个下午能搞定的模块，现在两个小时就出原型了。

但这种快感背后，总得提着一根弦。

这次事件让我意识到，我们可能高估了这些工具的「懂事」程度。

它们很聪明，但它们没有价值观。

它们知道怎么把代码跑通，却不知道什么是「不能发的」。

所以，别把公司密钥当成私事，也别把默认设置当成保险。

在这个 AI 工具满天飞的时代，最大的风险，往往不是工具不够强，而是我们太信任它了。
